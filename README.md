# kcp-file-sender

> 用 KCP 取代 TCP，在高丢包、高延迟的跨国链路上把文件传输速度提升两个数量级。

---

## 背景

这个项目起源于一个非常具体的困境：一台海外服务器，一台本地机器，两者之间的网络质量不佳——RTT 约 270ms，ICMP 丢包率约 17%。

用 `wget` 走 TCP 下载一个文件，速度只有 **10 KB/s**。按这个速率，一个 3.5 GB 的文件需要大约 **4 天**。

但这不是链路的问题。同一台服务器，从其他地理位置访问速度正常；用裸 UDP 硬灌，能跑到 300 KB/s 以上。瓶颈完全在于 **TCP 的拥塞控制机制**。

### 为什么 TCP 这么慢

TCP 的经典拥塞控制算法（CUBIC、Reno）有一个根深蒂固的设计假设：**丢包 = 网络拥塞**。

一旦检测到丢包，它就主动降低发送窗口，放缓发送速率。这在 1980 年代的同质有线网络里是合理的——那时候丢包基本等于路由器队列溢出。

但在今天的跨国链路上，丢包的原因往往是：

- 中间设备的随机丢包（策略、限速、缓存不足）
- 链路误码
- 运营商互联点的拥塞

这些丢包**并不代表发送端应该减速**。TCP 无法区分这两者，于是频繁降窗，窗口被压到极小，吞吐被锁死在 `MSS/RTT × f(丢包率)` 的水平。

用近似公式估一下：

```
吞吐 ≈ (MSS / RTT) × C / √p
```

取 MSS=1460B、RTT=270ms、丢包率 p=5%：

```
1460 / 0.27 × 1.22 / 0.224 ≈ 29 KB/s
```

数量级和实测的 10 KB/s 吻合。**TCP 在这个路径上被自己的假设困住了。**

### BBR 也不行

BBR 改进了这一点——它不把丢包直接当作拥塞信号，而是基于带宽和 RTT 建模。但在丢包率超过 20% 的路径上，BBR 的 probe 机制也会退化，因为它同样需要丢包作为探测信号。

换句话说：**只要协议栈还试图"合理地"响应丢包，它在这个路径上就跑不快。**

## 原理

既然丢包不是拥塞，那就不应该对丢包做出任何减速反应。这是本项目的核心思路。

### 用 KCP 替代 TCP

[KCP](https://github.com/skywind3000/kcp) 是一个基于 UDP 的可靠传输协议，它保留了 TCP 的所有可靠性保证（有序、不丢、不重），但**把拥塞控制变成了可选**。

关键的参数是 `nc`（no congestion control）：

```go
conn.SetNoDelay(1, 10, 2, 1)  // 最后一个 1 = 关闭拥塞控制
```

关闭后，KCP 收到丢包只会触发重传，**不会降低发送速率**。这正是这个路径上需要的语义。

### FEC：用冗余换重传

KCP 内置 Reed-Solomon 前向纠错（FEC）。参数 `(dataShard, parityShard)` 表示每 `dataShard` 个数据分片，额外生成 `parityShard` 个纠错分片。

例如 `(10, 3)`：

- 发送 10 个数据包，附带 3 个冗余包
- 接收端只要收到任意 10 个，就能还原全部 10 个原始数据
- 能直接容忍最多 **3 个包丢失**，无需重传

丢包率 17% 时，10 个包期望丢 1.7 个，FEC 完全可以覆盖。这意味着大部分丢包**根本不触发重传**，延迟和吞吐都更稳定。

代价是 23% 的带宽开销。但如果带宽本来就有富余，这个代价换来的是几倍的吞吐提升，非常划算。

### 为什么需要它：数据对比

同一个路径，同一个文件：

| 协议        | 配置                  | 速率             |
| ----------- | --------------------- | ---------------- |
| TCP (wget)  | CUBIC                 | **10 KB/s**      |
| TCP (wget)  | BBR                   | 约 15 KB/s       |
| 裸 UDP 原型 | 无拥塞控制，无 pacing | 0.3 MB/s（会崩） |
| **KCP**     | **FEC 10/3, nc=1**    | **0.92 MB/s**    |

从 10 KB/s 到 0.92 MB/s，约 **92 倍**。

裸 UDP 原型虽然也能绕过 TCP 的限速，但由于没有窗口管理和 pacing，很快把路径灌爆，进入重传风暴。KCP 在此基础上加上了合理的重传策略和滑动窗口，能在激进和稳定之间取得平衡。

## 它做了什么

一个简单的命令行工具，分为服务端和客户端：

**服务端**

- 递归扫描指定目录
- 找出所有大于指定大小的文件（默认按 MiB 计）
- 按相对路径字典序编号
- 等待客户端连接，推送文件列表

**客户端**

- 连接服务端，获取文件列表
- 用户输入一个或多个序号（空格分隔）
- 逐个下载到本地，自动处理重名（`a.bin` → `a_1.bin`）
- 显示 wget 风格的进度条（速率、百分比、ETA）
- 完成后输出统计并退出

## 使用

### 编译

```bash
go mod init kcp-file-sender
go get github.com/xtaci/kcp-go/v5@latest
go build -o kcpfile main.go
```

### 服务端

```bash
./kcpfile -mode server -path /data/files -minsize 200 -port 12080
```

- `-path`：扫描根目录（递归）
- `-minsize`：最小文件大小，单位 MiB（默认 0）
- `-port`：监听端口（默认 12080）

### 客户端

```bash
./kcpfile -mode client -server <serverIP> -port 12080 -out ./downloads
```

- `-server`：服务端地址
- `-port`：端口（默认 12080）
- `-out`：保存目录（默认当前目录）

### 调参

所有 KCP 参数都有默认值，可在两端分别覆盖：

| 参数          | 默认 | 说明                        |
| ------------- | ---- | --------------------------- |
| `-fec-data`   | 10   | FEC 数据分片数              |
| `-fec-parity` | 3    | FEC 纠错分片数              |
| `-interval`   | 10   | KCP 内部 tick，单位 ms      |
| `-resend`     | 2    | 快速重传触发的重复 ACK 阈值 |
| `-nodelay`    | 1    | nodelay 模式                |
| `-nc`         | 1    | 拥塞控制开关（1=关闭）      |
| `-window`     | 1024 | 收发窗口，单位分片          |
| `-mtu`        | 1400 | MTU                         |

调参建议：

- **丢包率高于 20%**：把 FEC 调大，如 `-fec-parity 5`
- **带宽富余、丢包率低**：把 FEC 调小，如 `-fec-parity 1`，减少冗余
- **RTT 很大**（>500ms）：适当增大 `-window` 到 2048 或 4096
- **CPU 吃紧**：把 `-interval` 调回 20 或 30

## 限制

这个工具为特定场景设计，并不通用：

- **没有加密**。KCP 层不做 TLS，数据在 UDP 上明文传输。不要在不受控网络上传输敏感数据。
- **没有认证**。任何能连上服务端端口的客户端都能获取文件列表并下载。
- **不处理 NAT 穿越**。需要客户端能直连服务端的 UDP 端口。
- **单客户端串行**。一次只服务一个连接，不并发。
- **无断点续传**。中途断开需要重新下载整个文件。
- **没有速率控制**。关闭拥塞控制意味着它会尽可能快地发送，在有其他流量的链路上可能抢占带宽。

如果你的网络环境没有高丢包问题，或者丢包主要来自真正的拥塞，**不需要这个工具**。TCP 在这种情况下表现更好，也更公平。

## 适用场景

- 跨国链路，RTT 高、随机丢包明显
- 家用宽带到海外 VPS 拉大文件
- 无线/卫星链路，误码丢包为主
- 服务器到本地，带宽有富余但协议栈不配合
