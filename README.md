# kcp-file-sender

> 用 KCP 取代 TCP，在高丢包、高延迟的跨国链路上把文件传输速度提升两个数量级。

---

## 背景

这个项目起源于一个非常具体的困境：一台海外服务器，一台本地机器，两者之间的网络质量不佳——RTT 约 270ms，ICMP 丢包率约 17%。

用 `wget` 走 TCP 下载一个文件，速度只有 **10 KB/s**。按这个速率，一个 3.5 GB 的文件需要大约 **4 天**。

但这不是链路的问题。同一台服务器，从其他地理位置访问速度正常；用裸 UDP 硬灌，能跑到 300 KB/s 以上。瓶颈完全在于 **TCP 的拥塞控制机制**。

### 为什么 TCP 这么慢

TCP 的经典拥塞控制算法（CUBIC、Reno）有一个根深蒂固的设计假设：**丢包 = 网络拥塞**。

一旦检测到丢包，它就主动降低发送窗口，放缓发送速率。这在 1980 年代的同质有线网络里是合理的——那时候丢包基本等于路由器队列溢出。

但在今天的跨国链路上，丢包的原因往往是：

- 中间设备的随机丢包（策略、限速、缓存不足）
- 链路误码
- 运营商互联点的拥塞

这些丢包**并不代表发送端应该减速**。TCP 无法区分这两者，于是频繁降窗，窗口被压到极小，吞吐被锁死在 `MSS/RTT × f(丢包率)` 的水平。

用近似公式估一下：

```
吞吐 ≈ (MSS / RTT) × C / √p
```

取 MSS=1460B、RTT=270ms、丢包率 p=5%：

```
1460 / 0.27 × 1.22 / 0.224 ≈ 29 KB/s
```

数量级和实测的 10 KB/s 吻合。**TCP 在这个路径上被自己的假设困住了。**

### BBR 也不行

BBR 改进了这一点——它不把丢包直接当作拥塞信号，而是基于带宽和 RTT 建模。但在丢包率超过 20% 的路径上，BBR 的 probe 机制也会退化，因为它同样需要丢包作为探测信号。

换句话说：**只要协议栈还试图"合理地"响应丢包，它在这个路径上就跑不快。**

---

## 原理

既然丢包不是拥塞，那就不应该对丢包做出任何减速反应。这是本项目的核心思路。

### 用 KCP 替代 TCP

[KCP](https://github.com/skywind3000/kcp) 是一个基于 UDP 的可靠传输协议，它保留了 TCP 的所有可靠性保证（有序、不丢、不重），但**把拥塞控制变成了可选**。

关键的参数是 `nc`（no congestion control）：

```go
conn.SetNoDelay(1, 10, 2, 1)  // 最后一个 1 = 关闭拥塞控制
```

关闭后，KCP 收到丢包只会触发重传，**不会降低发送速率**。这正是这个路径上需要的语义。

### FEC：实测无效，默认关闭

KCP 内置 Reed-Solomon 前向纠错（FEC）。参数 `(dataShard, parityShard)` 表示每 `dataShard` 个数据分片，额外生成 `parityShard` 个纠错分片，接收端收到任意 `dataShard` 个即可还原全部原始数据。

理论上这能减少重传——丢包率 17% 时，10 个包期望丢 1.7 个，附带几个 parity 包似乎就能覆盖。

**但实测下来并非如此。**

同一路径、同一文件，对比开启与关闭 FEC：

| 配置                     | 速率          | 相对提升 |
| ------------------------ | ------------- | -------- |
| FEC 10/3（23% 冗余开销） | 0.92 MB/s     | 1.00×    |
| **FEC 关闭**             | **1.20 MB/s** | **1.30×** |

关闭 FEC 后速率提升到 1.30 倍，几乎正好等于 FEC 的冗余比例（10 数据 + 3 纠错，开销 3/10 = 30%）。这说明：

- FEC 并没有有效减少重传——重传该发生的还是发生了；
- 额外生成的 parity 包本身也在高丢包路径上大量丢失，多数时候凑不齐还原所需的分片；
- 结果只是把 30% 的带宽白白消耗在冗余包上，实际有效吞吐反而下降。

因此本项目的默认配置是：

```
-fec-data 0 -fec-parity 0   # 不开启 FEC
```

高丢包路径下，靠 KCP 自身的快速重传 + 关闭拥塞控制，已经能获得足够吞吐，叠加 FEC 只会适得其反。

### 为什么需要它：数据对比

同一个路径，同一个文件：

| 协议        | 配置                          | 速率             |
| ----------- | ----------------------------- | ---------------- |
| TCP (wget)  | CUBIC                         | **10 KB/s**      |
| TCP (wget)  | BBR                           | 约 15 KB/s       |
| 裸 UDP 原型 | 无拥塞控制，无 pacing         | 0.3 MB/s（会崩） |
| KCP         | nc=1，FEC 10/3（早期配置）    | 0.92 MB/s        |
| **KCP**     | **nc=1，FEC 关闭（当前默认）** | **1.20 MB/s**    |

从 10 KB/s 到 1.20 MB/s，约 **120 倍**。

裸 UDP 原型虽然也能绕过 TCP 的限速，但由于没有窗口管理和 pacing，很快把路径灌爆，进入重传风暴。KCP 在此基础上加上了合理的重传策略和滑动窗口，能在激进和稳定之间取得平衡。

## 它做了什么

一个简单的命令行工具，分为服务端和客户端：

**服务端**

- 递归扫描指定目录
- 找出所有大于指定大小的文件（默认按 MiB 计）
- 按相对路径字典序编号
- 等待客户端连接，推送文件列表
- **单次会话**：处理完一个客户端的连接后直接退出，需要重新启动才能服务下一个客户端

**客户端**

- 连接服务端，获取文件列表（并显示总文件数与总字节数）
- 用户输入序号（空格分隔），支持：
  - 单个序号：`3`
  - 闭区间范围：`1-4`（含首尾）
  - 全部：`all`
  - 混合：`1-4 7 9-10`
- 下载前先做本地预检，并显示选中文件累计字节数、本次需传输字节数
- 逐个下载到 `-out` 指定目录，显示 wget 风格的进度条（速率、百分比、ELP/ETA）
- 完成后输出统计并退出

**同名文件的处理**

客户端按文件名（`filepath.Base`）保存到 `-out` 目录，下载前会对每个选中文件做本地预检：

| 本地同名文件状态   | 处理方式                         |
| ------------------ | -------------------------------- |
| 不存在             | 从 0 开始下载                    |
| 大小等于服务端     | 视为已完成，**跳过**             |
| 大小小于服务端     | 从本地大小处**断点续传**         |
| 大小大于服务端     | 视为异常，**警告并跳过**（需人工处理） |

因此**不会产生重名冲突，也不会重命名文件**——已下载的部分会被识别并跳过，未下载的部分会被续传。

## 使用

### 编译

```bash
go mod init kcp-file-sender
go get github.com/xtaci/kcp-go/v5@latest
go build -o kcpfile main.go
```

### 服务端

```bash
./kcpfile -mode server -path /data/files -minsize 200 -port 13080
```

- `-path`：扫描根目录（递归）
- `-minsize`：最小文件大小，单位 MiB（默认 0）
- `-port`：监听端口（默认 13080）

### 客户端

```bash
./kcpfile -mode client -server <serverIP> -port 13080 -out ./downloads
```

- `-server`：服务端地址
- `-port`：端口（默认 13080）
- `-out`：保存目录（默认当前目录）

### 选择文件示例

```
输入序号 (空格分隔, 支持 1-4 范围与 all, q 退出): 1-4 7
```

选择第 1、2、3、4、7 个文件。

```
输入序号 (空格分隔, 支持 1-4 范围与 all, q 退出): all
```

下载全部文件。

> `all` 不能与其他序号混用（如 `all 1-4` 会报错）；范围必须升序（`4-1` 会报错）；`-` 两侧不能有空格。

### 断点续传

对每个选中文件，客户端会先 `stat` 本地同名文件：

- 不存在：从 0 开始
- 大小相等：跳过
- 本地更小：从本地大小的位置开始续传（`offset = 本地大小`），服务端用 `seek` 从对应位置发送
- 本地更大：视为异常，跳过并警告

因此**中途断开后重新运行相同的选择即可从断点继续**，无需重新下载整个文件。

### 调参

所有 KCP 参数都有默认值，可在两端分别覆盖：

| 参数          | 默认 | 说明                              |
| ------------- | ---- | --------------------------------- |
| `-fec-data`   | 0    | FEC 数据分片数（0 = 关闭 FEC）    |
| `-fec-parity` | 0    | FEC 纠错分片数（0 = 关闭 FEC）    |
| `-interval`   | 10   | KCP 内部 tick，单位 ms            |
| `-resend`     | 2    | 快速重传触发的重复 ACK 阈值       |
| `-nodelay`    | 1    | nodelay 模式                      |
| `-nc`         | 1    | 拥塞控制开关（1=关闭）            |
| `-window`     | 512  | 收发窗口，单位分片                |
| `-mtu`        | 1400 | MTU                               |

调参建议：

- **FEC 默认保持关闭**。如"原理"一节所述，在高丢包路径上实测开启 FEC 反而更慢，冗余开销直接转化为带宽浪费。仅在丢包率很低（如 < 5%）且偶发突发丢包、希望降低重传延迟时，才可尝试极小参数（如 `-fec-parity 1`）。
- **RTT 很大**（>500ms）：适当增大 `-window` 到 1024 或 2048。
- **CPU 吃紧**：把 `-interval` 调回 20 或 30。

## 限制

这个工具为特定场景设计，并不通用：

- **没有加密**。KCP 层不做 TLS，数据在 UDP 上明文传输。不要在不受控网络上传输敏感数据。
- **没有认证**。任何能连上服务端端口的客户端都能获取文件列表并下载。
- **不处理 NAT 穿越**。需要客户端能直连服务端的 UDP 端口。
- **单次会话服务**。服务端只处理一个客户端的一次会话，传输结束后进程退出，需要手动重启才能服务下一个客户端；不支持并发多客户端。
- **不保留目录结构**。客户端按文件名（`filepath.Base`）保存到 `-out` 目录，服务端的相对路径层级会丢失；不同目录下的同名文件会落到同一路径，可能互相干扰（建议用不同的 `-out` 分开存放）。
- **没有速率控制**。关闭拥塞控制意味着它会尽可能快地发送，在有其他流量的链路上可能抢占带宽。

如果你的网络环境没有高丢包问题，或者丢包主要来自真正的拥塞，**不需要这个工具**。TCP 在这种情况下表现更好，也更公平。

## 适用场景

- 跨国链路，RTT 高、随机丢包明显
- 家用宽带到海外 VPS 拉大文件
- 无线/卫星链路，误码丢包为主
- 服务器到本地，带宽有富余但协议栈不配合
